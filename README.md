> **Proprietary software. Copyright (c) 2026 SROT AI LLP. All rights reserved.** See [LICENSE](LICENSE).

An all-in-one growth platform for agencies and small businesses: CRM, unified inbox, phone and SMS, calendars, forms, automations, sites and funnels, email marketing, payments, reputation, social, reporting, courses and AI agents, plus an agency layer to run, template, white label and resell client workspaces.

**Status:** [v0.2.0](https://github.com/anshnt/go-high/releases/latest) (`ghcr.io/anshnt/go-high`). Try the [public demo](https://anshnt.github.io/go-high/) (fictional data, runs in your browser).

Working today:

- **Platform**: organizations, brands and workspaces with row level security on every table; sign in with password or magic link; roles with record and field scopes; audit log; signed webhooks; `/api/v1` with cursors and idempotency.
- **CRM**: contacts, companies, deals and custom objects on one record engine, with filters, saved views, tags, links, bulk edit, a timeline and pipelines with exit rules and forecasts.
- **Work**: tasks with recurrence and dependencies, My Day, in-app notifications.
- **Conversations**: the unified inbox for SMS, email, WhatsApp and web chat, keyboard first and live, with consent checks, notes, snooze, assignment and a channel settings screen.
- **Capture**: forms, surveys and quizzes with logic and an embed; calendars with round robin and a public booking page.
- **Automation**: workflows as versioned graphs that walk a record through waits, conditions, goals and actions (fields, tags, owner, stage, tasks, messages with consent checks, notifications, webhooks), with a per-record trace, test runs on a virtual clock and a "why did it not enter" answer (API only so far; the builder is next).

Next: the pipeline board and workflow builder screens, email marketing and payments (see the [roadmap](docs/PLAN.md#roadmap)).

## Quick start

From a clone, build and run everything locally:

```bash
docker compose up --build
```

Open http://localhost:8000 (API docs at `/api/docs`). The `worker` service runs background jobs from the same image.

### Run a release

Releases publish `ghcr.io/anshnt/go-high:<version>` (and `:latest`). With this repository's `docker-compose.yml` and a `.env` copied from [.env.example](.env.example):

```bash
docker compose pull && docker compose up -d
```

Put it behind a TLS reverse proxy, set `PUBLIC_URL` to the https origin, `COOKIE_SECURE=1`, a long random `SECRET_KEY`, and `FORWARDED_ALLOW_IPS` to the proxy's address. `/api/health` reports the running version.

### Cutting a release

Tag `main` and push the tag; the Release workflow builds and publishes the image and creates the GitHub release with notes from the merged pull requests:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

### Without Docker

Needs Python 3.13 with [uv](https://docs.astral.sh/uv/), Node 22 and a PostgreSQL 16+ server.

```bash
cd backend && uv sync && DATABASE_URL=postgresql+psycopg://user:pass@127.0.0.1:5432/gohigh uv run uvicorn app.main:app --reload
```

```bash
cd backend && uv run python -m app.worker
```

```bash
cd frontend && npm install && npm run dev
```

The dev server proxies `/api` to `127.0.0.1:8000`; set `VITE_API_TARGET` to use another API. Sign in at `/signin`, or create an account at `/signup` (cookie-authenticated writes need the page origin in `PUBLIC_URL`, `127.0.0.1:5173` and `localhost:5173` are in the default). With `DEV_EXPOSE_MAGIC_LINKS=1` the sign-in screen shows a "Dev only: open sign-in link" button, so no mail is needed locally.

Tests use a real Postgres and create the `gohigh_test` database if it is missing (`TEST_DATABASE_URL` overrides the server):

```bash
cd backend && uv run pytest
```

Tests marked `perf` check speed (20 000 contacts, a filtered, sorted page in under 300 ms) and depend on the machine; leave them out with `uv run pytest -m "not perf"`.

For a coverage report add `--cov=app --cov-report=term-missing` (pytest-cov is a dev dependency); CI runs the suite without it and sets no threshold.

Background jobs: register a handler with `@jobs.handler("kind")` and call `jobs.enqueue(db, "kind", payload, run_at=...)` inside your transaction. Failed jobs retry with exponential backoff (10 s doubling, capped at 1 hour) and become `dead` after `max_attempts`.

## Tenancy and auth

Organization > Brand > Workspace. A user belongs to orgs and optionally to single workspaces, each with a role (see [Roles, permissions and audit](#roles-permissions-and-audit)); org owners and admins are admins of every workspace in their org. Sign in with email + password or a magic link (`/api/auth/*`, `/api/me`); password hashes are in `user_credentials`, not `users`, where a session reaches only its own user's row; the session is an HttpOnly, SameSite=Lax cookie whose SHA-256 is the only thing stored. Sessions have an idle timeout and an absolute expiry, can be listed and revoked (`/api/auth/sessions`), and cookie-authenticated writes whose `Origin` header is not in `PUBLIC_URL` get a 403.

Choose the workspace per request with the `X-Workspace-Id` header. The `in_workspace` dependency (`app/security.py`) answers 404 for any workspace the user cannot access, then sets `app.workspace_id` and `app.org_id` for the request; routes that only need the user take the `user` dependency. `GET /api/workspaces/current` echoes the active workspace.

Isolation is enforced by Postgres, not by remembering a `WHERE`. Request handlers get a session from `app.security.user`, which runs every transaction as the NOLOGIN, non-owner role `gohigh_app` (`SET LOCAL ROLE`) with `app.user_id`, `app.org_id`, `app.workspace_id` set, and all tenant tables use `FORCE ROW LEVEL SECURITY`. Superusers and table owners bypass RLS, so migrations and the worker keep the owner role and the API never queries tenant tables with it. Sign up, sign in and magic links run as `gohigh_app` with `app.system = 'on'` (the `system` policy on each auth table); nothing else sets it.

A new workspace-scoped table in a module migration:

```sql
CREATE TABLE contacts (id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
                       workspace_id uuid NOT NULL REFERENCES workspaces (id) ON DELETE CASCADE, ...);
ALTER TABLE contacts ENABLE ROW LEVEL SECURITY;
ALTER TABLE contacts FORCE ROW LEVEL SECURITY;
CREATE POLICY workspace ON contacts USING (workspace_id = app_workspace_id()) WITH CHECK (workspace_id = app_workspace_id());
GRANT SELECT, INSERT, UPDATE, DELETE ON contacts TO gohigh_app;
```

`tests/test_isolation.py` calls every `/api` route as a user of one org with the ids of another and runs the same checks in SQL. Settings: `PUBLIC_URL` (comma separated allowed origins, the first builds magic links), `COOKIE_SECURE` (default 1; use 0 on plain http), `SESSION_IDLE_MINUTES`, `SESSION_ABSOLUTE_HOURS`, `MAGIC_LINK_MINUTES`, `LOGIN_MAX_FAILURES`, `LOGIN_WINDOW_MINUTES`. Magic links are logged at INFO until the email module exists; `DEV_EXPOSE_MAGIC_LINKS=1` also returns them in the response, so never set it outside local development and tests.

## API conventions

Public routes live under `/api/v1/<resource>` (ADR 0003) and follow these rules; the older `/api/auth`, `/api/me` and `/api/workspaces` routes keep their `{"detail": ...}` errors. The workspace comes from `X-Workspace-Id`, as above. The unauthenticated `/api/public` routes (booking pages, [Calendars and booking](#calendars-and-booking)) use the same error envelope; their workspace comes from the link.

- **Errors**: every error on `/api/v1` is `{"error": {"code": "validation_failed", "message": "...", "fields": {"url": "must use https"}, "trace_id": "..."}}`. `fields` appears for validation errors, with dotted paths such as `event_types.0`. `trace_id` equals the `x-request-id` response header and the id in the logs. Raise `app.api.ApiError(status, code, message, fields)` for a coded error.
- **Pagination**: cursor only, `?limit=50&cursor=...` (1 to 200); lists answer `{"data": [...], "next_cursor": "..." | null}`, newest first. The cursor is opaque, a base64 sort key plus id signed with HMAC-SHA256 under `SECRET_KEY`, so it cannot be edited or forged (a bad one is a 400 `invalid_cursor`). Set `SECRET_KEY` to the same value on every API replica; the development default logs a warning. Use `app.api.paginate`.
- **Idempotency**: send `Idempotency-Key` (1 to 255 characters) on a POST. The first successful response is stored for 24 hours per workspace. The same key from the same user with the same method, path, query and body returns that response again with `Idempotent-Replayed: true`; the same key with anything else (another user included, since a response depends on what its user may see) is a 409 `idempotency_key_reused`. Failed requests store nothing, so they can be retried. A route opts in with `idem: Idem = Depends(idempotency)` (after its role dependency) and ends with `return idem.commit(201, body)`, which commits the work and the stored response in one transaction, so a retry can never repeat the work. A create that returns a secret returns the same secret on a replay.

## Events and webhooks

Every state change is an event, written by `events.emit(db, "type", "subject_type", subject_id, data, actor=("user", user_id))` in the same transaction as the change: it exists only if the change commits. The workspace is the request's (or pass `workspace_id=`). Each type needs a JSON schema in `backend/app/event_types/<type>.json`; `emit` refuses unknown types and data that misses required keys or adds unexpected ones, and a test fails when code emits a type without a schema. Types so far: `workspace.created`, `user.signed_up`, `webhook_endpoint.created`, `webhook.test`, and the record engine's `record.created`, `record.updated`, `record.deleted`, `record.restored`, `deal.stage_changed`, `association.created`, `association.deleted`, `tag.created`, `tag.updated`, `tag.deleted`, `tag.merged`, `tag.added`, `tag.removed`, the tasks' `task.created`, `task.updated`, `task.completed`, `task.deleted`, the inbox's (see Inbox and channels) `message.*`, `conversation.*`, `channel.*` and `consent.changed`, and the configuration and security events of the audit log (`object.*`, `field.*`, `association_type.*`, `pipeline.*`, `stage.*`, `stages.reordered`, `role.*`, `team.*`, `member.role_changed`, `webhook_endpoint.updated`, `.deleted`, `.secret_revealed` and `.secret_rotated`, `user.password_changed`, `auth.sessions_revoked`, `audit.exported`), and the forms' `form.created`, `form.updated`, `form.published`, `form.deleted`, `form.restored`, `form.submitted`. A bulk change uses `events.emit_many(db, type, subject_type, [(subject_id, data), ...])`: one insert and one dispatcher wake-up.

Consumers read the log with `events.read_batch(db, "name")` and `events.advance(db, "name", batch)` in one transaction. A plain `id > last_id` cursor can skip an event whose transaction commits late; `read_batch` only returns events of transactions older than every transaction still open (`txid < pg_snapshot_xmin(pg_current_snapshot())`, in `(txid, id)` order), so nothing is skipped. The price is that one long transaction delays every consumer: keep request transactions short and commit bulk work in batches. Register a batch processor with `@events.consumer("name")`; the `events.dispatch` job (queued by every `emit`, run by the worker) calls each one and asks to be run again while events are waiting behind an open transaction. Run the worker for any of this to happen.

Webhooks are managed by roles with `webhooks.manage` (workspace admins) at `/api/v1/webhooks`: `POST` (the signing secret is returned once, here only), `GET`, `GET /{id}`, `PATCH /{id}` (`url`, `event_types`, `filter`, `active`), `DELETE /{id}`, `POST /{id}/test` (emits `webhook.test` to that endpoint only), `POST /{id}/reveal-secret` (the signing secret again, recorded as `webhook_endpoint.secret_revealed`), `POST /{id}/rotate-secret` (a new secret, returned there; the old one stops working at once; `webhook_endpoint.secret_rotated`), `GET /{id}/deliveries?status=&type=&from=&to=` (`type` is a type or a family, `record.*`; `from` and `to` bound when the delivery was made), `GET /deliveries/{id}` (one delivery with the JSON body and headers it sends), `POST /deliveries/{id}/replay` and `GET /event-types` (the catalog: every type with its description and data schema). Settings > API and webhooks (`/settings/api`) is the screen for all of it. `event_types` is a list of registered types or `"*"`; `filter` is a JSON object that the event's `data` must contain. An endpoint only gets events from after it was created.

Each matching event becomes one delivery, sent by a `webhook.deliver` job as a `POST` of JSON (`id`, `type`, `workspace_id`, `occurred_at`, `subject`, `actor`, `data`) with the headers `GoHigh-Event-Id`, `GoHigh-Event-Type`, `GoHigh-Delivery-Id` and `GoHigh-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "<t>.<body>")>`. Any 2xx is success. A timeout (10 s), a redirect (never followed) or another status is retried with the job queue backoff, up to 12 attempts; after 3 days of only failures the endpoint is disabled (`disabled_reason`; re-enable it with `PATCH`). The log keeps the status, attempts, response status, time and the first 2 KB of the response. A replay is a new delivery of the same event, with the same `GoHigh-Event-Id`, so receivers can dedupe. Deliveries are not ordered: two events can arrive in either order, so compare `occurred_at` (or the event `id`, which increases) instead of relying on arrival order. Verify a delivery on your side with the raw request body, before parsing it, and reject timestamps older than 5 minutes:

```python
import hashlib, hmac, time

def verify(secret: str, signature_header: str, body: bytes, tolerance: int = 300) -> bool:
    parts = dict(p.split("=", 1) for p in signature_header.split(","))
    expected = hmac.new(secret.encode(), parts["t"].encode() + b"." + body, hashlib.sha256).hexdigest()
    return abs(time.time() - int(parts["t"])) <= tolerance and hmac.compare_digest(parts["v1"], expected)
```

Webhook URLs must be `https` and resolve to public addresses only (no private, loopback, link-local, CGNAT, multicast or reserved space, IPv4-mapped forms included). The check runs when the URL is saved and again before every send; the request then connects to the address it just checked, with the original host in the `Host` header and the TLS handshake, so a DNS answer that changes in between cannot redirect it. For local development, `ALLOW_HTTP_WEBHOOKS=1` allows plain http and `WEBHOOK_ALLOW_IPS=127.0.0.1` (exact addresses, comma separated, only honoured with the first setting) lets a receiver on your machine through. Never set either on a reachable server.

## Channel adapters

`app/channels/` is the messaging provider layer of ADR 0005: library code with no tables and no routes, so the inbox webhook handler and the `message.send` job call it the same way. One module per provider (`twilio`, `telnyx`, `smtp`, `mailgun`, `meta_whatsapp`); Amazon SES is the SMTP adapter pointed at its SMTP endpoint. `channels.ADAPTERS` maps a `channels.provider` value to its module, and every module has the same three functions:

```python
from app.channels import ADAPTERS
from app.channels.base import Channel, Outbound, Request

adapter = ADAPTERS[row.provider]
channel = Channel(address=row.address, config=row.config, secrets=decrypted_secret)  # secrets never live in config
ok = adapter.verify(channel, Request(url, headers, raw_body))  # False when unsigned, wrongly signed or stale
items = adapter.parse(Request(url, headers, raw_body))         # list[Inbound]; ValueError on a body the provider would not send
result = adapter.send(channel, Outbound(to=..., from_=..., body=..., idempotency_key=str(message.id)))  # SendResult
```

- `Request` is the webhook as received: the full URL it was called on (behind a proxy, the public one; Twilio signs it, so `twilio.verify` also takes `public_url=`), the headers and the raw body bytes. Verify before parsing, on the raw bytes. Meta's GET handshake is `meta_whatsapp.challenge(channel, request)`: answer 200 with the returned text, or 403 on `None`.
- `parse` returns `Inbound` items: kind `message` (status `received`) or `status` (`queued`, `sent`, `delivered`, `read`, `failed`; email adds `complained` and `unsubscribed`, which are opt-out signals, not message states). Reports can arrive out of order, so never move a message backwards. `thread_ref` is the provider id of the message being replied to; email ids are stored without angle brackets.
- `send` raises `ChannelError`. `retryable` is true for timeouts, connection errors, 408, 429, 5xx, SMTP 4xx replies and Meta's throttling codes, false for everything a retry cannot fix (bad credentials, an invalid number, a refused address). `code` is the provider's own, for example Twilio 21610 for a recipient who replied STOP. A retried job must reuse the same `idempotency_key`: Twilio gets it as a header, SMTP and Mailgun derive the Message-ID from it; Telnyx and WhatsApp have no idempotency, so the job checks for an existing provider id first.
- Provider hosts are fixed (stdlib `http.client`, 10 s timeouts). Hosts a user configures never are: the SMTP host goes through `app/ssrf.py` (public addresses only, connecting to the address that was checked while the name stays the TLS server name), as do the URLs of email attachments (10 MB in all). SMTP has no plaintext mode: `starttls` (587) or `tls` (465), and a server without STARTTLS is refused.
- Settings per provider (`config` and `secrets` keys) are listed at the top of each module. `send` takes a keyword-only `base_url` for tests. A module may also have `check(channel)`, which asks the provider to accept the credentials without sending anything (Twilio, Telnyx, Mailgun, WhatsApp and SMTP have one) and raises `ChannelError` when refused.

`app/compliance.py` holds the pure rules the send path needs: `can_send(kind, now, consent=, zones=, quiet=, replying=, sent=, cap=)` (None, or a `Refusal(code, reason, retry_at)` for an opt-out, do not disturb, quiet hours or a frequency cap), `phone_zones(e164)`, `keyword(body)` (STOP, START, HELP lists, whole message only), `quiet_until(now, tz, start, end)` (next allowed time in the contact's zone, DST safe), `sms_segments(body)` (GSM-7 with the extension table, or UCS-2, as `(encoding, segments, chars)`) and `email_risk(subject, html, text, bulk)` (lint warnings). Their tests, with the adapter tests, are in `backend/tests/channels/` and need no database.

## Records and data model

One engine serves contacts, companies, deals and custom objects (ADR 0002), with the same routes, filters, views, associations, timeline and events for all of them. Everything is under `/api/v1`, uses the conventions above and the `X-Workspace-Id` header. What a user may do with them is their role's (capabilities, record scope and field rules, below): a Member reads and writes records and applies tags, changing the schema (objects, fields, association types) and renaming, merging or deleting tags is for admins.

- **Objects and fields are rows.** `GET/POST /objects`, `GET/PATCH/DELETE /objects/{key}` (DELETE archives; `PATCH {"archived": false}` brings it back) and `GET/POST /objects/{key}/fields`, `PATCH/DELETE /objects/{key}/fields/{field_key}` and `POST /objects/{key}/fields/reorder` with `{"keys": [...]}`, every live field once (one `field.updated` per field that moved; fields the caller's role hides keep their places). Settings > Objects and fields (`/settings/fields`) makes and edits objects, fields and association types. A field's key and type never change; archiving hides it everywhere and keeps its values. There is no cap on custom objects (a new one starts with a required `name` field); changing an object's `primary_fields` renames every record at once. Every workspace starts with `contact`, `company` and `deal` and their fields, seeded by one function (`records.seed.seed_workspace`, called at sign up and by `POST /api/workspaces`; migration 0004 backfilled existing workspaces).
- **Field types**: `text`, `long_text`, `number`, `money` (`{"amount": 1999, "currency": "USD"}`: integer minor units, ISO 4217), `date`, `datetime` (ISO 8601 with a zone, stored in UTC), `boolean`, `select`, `multi_select` (they store choice ids), `stage` (a stage id, see Pipelines and deals), `email` (stored lower case), `phone` (stored as E.164; a number without `+` is read with the field's `options.region`, else `DEFAULT_PHONE_REGION`, default `US`), `url`, `user`, `record` (the id of a record of `options.object`), and `formula` and `rollup`, which are stored but read-only and not computed yet. `records.types.validate(field, value)` is the one validator; `rules` hold `required`, lengths, `min` and `max`.
- **Records**: `GET/POST /objects/{key}/records`, `GET/PATCH/DELETE /objects/{key}/records/{id}`, `POST /objects/{key}/records/{id}/restore` and `GET /trash?object={key}`. `POST /objects/{key}/records/delete` and `/restore` take `{"ids": [...]}` (1 to 1000) and move them all or none (one missing or invisible id is a 404 and nothing changes), with one `record.deleted` or `record.restored` event each; they answer `{"deleted": n}` or `{"restored": n}`. A create, patch or get takes `?include=tags` like a list. A patch sets the values it sends and a null clears one; an invalid record is a 422 whose `fields` are `values.<key>`. `display_name` (the object's primary fields, then email, then phone), `email_norm` and `phone_e164` are derived on every write. A delete goes to the trash and a record outside the caller's scope is a 404. `POST /objects/{key}/records/update` takes `{"ids": [...], "values": {...}, "owner_id"}` and applies the same change to all of them or none (`owner_id` null unassigns, left out keeps each owner); it answers `{"updated": n}`, counting only records that changed, each with its own `record.updated`. The list's bulk bar uses it to change the owner of the selected records, and to set or clear one field on all of them (Edit fields, with undo).
- **Listing**: `filter` (JSON), `sort` (`-updated_at,display_name`, up to three, empty values last), `q`, `limit`, `cursor`, `include` (`tags` and the key of any associated object), `count=true` for a `total`, and `view=<saved view id>`. A long filter goes in the body of `POST /objects/{key}/records/query`, which takes the same names. Cursors are signed and belong to the sort that made them. `q` is full text over the display name and every text value, each word matched as a prefix (`ada lov`, `ada@ex`, `+1415`), best match first.
- **Filters** are one JSON language (ADR 0002): `{"and": [...]}`, `{"or": [...]}`, `{"not": {...}}`, `{"tag": "vip"}` (a tag name or id) and `{"field": key, "op": op, "value": value}`. A field is one of the object, `id` (a record's own id, with `is` and `in`, so the names behind a list of links come in one query), `display_name`, `owner_id`, `created_by`, `created_at`, `updated_at`, or a field of an associated object as `company.name` or `company.id` (compiled to `EXISTS`, in both directions). Every field, operator and value is checked against the field's type, and a mistake is a 400 `validation_failed` whose `fields` point at the node (`filter.and.1.field`); a filter never becomes SQL.

  | type | operators |
  | --- | --- |
  | `text`, `long_text`, `email`, `phone`, `url` | `is`, `is_not`, `contains`, `starts_with`, `in`, `not_in`, `is_empty`, `is_not_empty` |
  | `number`, `money` | `is`, `is_not`, `gt`, `gte`, `lt`, `lte`, `between`, `in`, `not_in`, `is_empty`, `is_not_empty` (money compares amounts of the same currency) |
  | `date`, `datetime` | the same, plus `within_last` and `older_than` with `{"days": 30}` (minutes, hours, days, weeks, months or years) |
  | `boolean` | `is`, `is_not`, `is_empty`, `is_not_empty` |
  | `select`, `stage`, `user`, `record` | `is`, `is_not`, `in`, `not_in`, `is_empty`, `is_not_empty` |
  | `multi_select` | `contains`, `in`, `not_in`, `is_empty`, `is_not_empty` |

  Recent leads that are tagged `vip` or have a deal over $5 000, newest first, with their tags and company:

  ```bash
  curl -G "$API/api/v1/objects/contact/records" -b cookies.txt -H "X-Workspace-Id: $WORKSPACE" \
    --data-urlencode 'filter={"and": [{"field": "lifecycle", "op": "is", "value": "lead"},
      {"field": "created_at", "op": "within_last", "value": {"days": 30}},
      {"or": [{"tag": "vip"}, {"field": "deal.amount", "op": "gt", "value": {"amount": 500000, "currency": "USD"}}]}]}' \
    --data-urlencode 'sort=-created_at' --data-urlencode 'include=tags,company' --data-urlencode 'limit=25'
  ```

- **Associations** link two records through a type with a label for each direction (contact "works at" company, company "employs" contact; deal to contact; deal to company). `GET/POST /association-types` and `DELETE /association-types/{id}` define more, between any two objects, so a custom Property links to contacts and deals; a type is `one_to_one`, `one_to_many` or `many_to_many`. `GET/POST /records/{id}/associations` lists links in both directions with the label as seen from that record, and creates one (the end that is the type's `from` side is found from the objects); `DELETE /associations/{id}` removes it. A link shows on the timeline of both records. A `record` field named like the object it links to and a type from this object to that one (a contact's `company` and "works at") stay in step: setting the field adds the link if it is missing, changing or clearing it removes the link to the old record, in the same transaction and with the same events as `POST /associations`. Links made by hand stay while the field does not change, and a link made by hand does not fill the field, so a list of a company's contacts filters on both: `{"or": [{"field": "company", "op": "is", "value": id}, {"field": "company.id", "op": "is", "value": id}]}`.
- **Tags** (any object): `GET/POST /tags` (usage counts, `q` prefix), `PATCH/DELETE /tags/{id}`, `POST /tags/{id}/merge` with `{"into": id, "preview": true}` to count what a merge would move and without `preview` to do it. `POST /records/{id}/tags` and `POST /records/tags` (up to 1000 `record_ids`) take `{"add": [tag ids], "remove": [tag ids]}` (ten tags in each list at most) and emit a `tag.added` or `tag.removed` event per change.
- **Saved views**: `GET/POST /views`, `GET/PATCH/DELETE /views/{id}` keep an object, a filter, columns and a sort; `?counts=true` adds a live `count`. A shared view belongs to the workspace and a private one to its owner (a row level security policy), and only the owner or an admin changes a shared one; a view carries its `owner_id`, so a screen can show the views of others as read only. A view is saved only if its filter compiles and its columns are fields, the columns of the record or `tags`.
- **Development data**: `cd backend && uv run python -m app.records.demo_seed <workspace_id>` fills an empty workspace with a fictional CRM (1000 contacts, 150 companies, 80 deals, 8 tags, the contacts' companies and the deals' links, four teammates), through the same write functions the API uses, in about half a minute. `--contacts`, `--companies` and `--deals` change the sizes. The content is the same every run; records are dated up to 14 months back.
- **Timeline**: `GET /records/{id}/timeline` is the record's events, newest first, with a cursor. Events about its own subject are found by subject; events that touch several records (a link) are listed in `event_records` by whoever emits them, with `records.timeline.link(db, event, record_ids)`, which notes, calls and messages will use too.
- **Permissions**: every read and write passes the hooks of ADR 0004 in `app/permissions.py`: `scope_filter(ctx, obj)` (a filter AST that is ANDed into every list, count, search, lookup, include and path filter), `redact(ctx, obj, values)` and `check_write(ctx, obj, changes)`. See Roles, permissions and audit, below.

## Pipelines and deals

Module 10 on the record engine. A deal is a record of the `deal` object, so it lists, filters, links and has a timeline like any record, and it needs no contact. Everything is under `/api/v1`; reading pipelines is `schema.read`, the board, its layout and the forecast are `deals.read`, moving a deal is `deals.write` (it is a write of the deal's stage, so a read-only `stage` field stops it), and changing pipelines and stages is `pipelines.manage` (Manager and Admin). Scope applies: a board, its counts and sums and the forecast hold only the deals the role may see. A role that hides `amount` gets counts without sums on the board and a 403 from the forecast; one that hides `stage` gets a 403 from both and no `deal.stage_changed` events.

- **Pipelines and stages are rows.** Every workspace starts with a Sales pipeline (Lead 10 %, Qualified 25 %, Proposal 50 %, Negotiation 80 %, Won 100 %, Lost 0 %), seeded with the system objects (`records.seed.add_pipeline`; migration 0007 gave existing workspaces one and turned their placeholder deal stages into these). `GET/POST /pipelines`, `GET/PATCH/DELETE /pipelines/{id}`, `POST /pipelines/{id}/stages`, `PATCH/DELETE /pipelines/{id}/stages/{stage_id}` and `POST /pipelines/{id}/stages/reorder` with `{"stage_ids": [...]}`, the whole order in one call. A stage has `name`, `kind` (`open`, `won` or `lost`), `probability` (0 to 100; won is 100 and lost is 0), `rotting_days` (null: never), `color` and `exit_rules`. A new pipeline without `stages` gets the Sales stages. `DELETE` removes a pipeline without deals (204) and archives one with deals (200, `archived_at` set); `PATCH {"archived": false}` brings it back; the last active pipeline cannot be archived or deleted, and a stage that holds deals, trashed ones too, cannot be deleted (409).
- **The `stage` field** of a deal holds a stage id of an active pipeline (else a 422 on `values.stage`). A deal created without one starts in the first open stage of the first pipeline; send `"stage": null` to have none. It has no `options`, cannot be sorted, and `stage_id` is the same value as a typed column, kept in step on every write, so the board reads one stage through an index (row level security keeps Postgres from using an index on a jsonb expression). Filters: `stage` takes ids with `is`, `is_not`, `in`, `not_in`, `is_empty` and `is_not_empty`, and two paths describe the stage without naming it: `{"field": "stage.kind", "op": "is", "value": "open"}` (`open`, `won` or `lost`) and `stage.pipeline` (a pipeline id), both with `is`, `is_not`, `in` and `not_in`. A deal with no stage has neither, so `stage.kind is_not open` includes it.
- **Moving a deal**: `POST /deals/{id}/move` with `{"stage_id", "after_id"?, "before_id"?, "position"?, "lost_reason"?, "lost_note"?}` and the card back, or a PATCH of `values.stage`; both go through `records.store.update`, so the rules are the same. The deal must meet the **exit rules** of the stage it leaves: a filter on the deal, such as `{"and": [{"field": "amount", "op": "is_not_empty"}, {"field": "close_date", "op": "is_not_empty"}]}`, judged on the deal as it will be after the change (a PATCH may supply what is missing). Failing is a 422 whose `fields` name each top level condition that does not hold (`values.close_date`: "Close date is required to leave Proposal"; `contact.email` for an association path; `exit_rules` for a nested `or`), and nothing changes. Rules that no longer compile, a field archived since, are a 409 until an admin fixes them. A lost stage needs `lost_reason` (the seeded select: price, timing, competitor, no decision, other; a 422 on `values.lost_reason`) and takes a `lost_note`; leaving a lost stage clears both. A change of stage emits `deal.stage_changed` next to `record.updated`: from and to stage (ids, names, kinds), `pipeline_id` and `seconds_in_stage`, counted from the previous stage change, else from the deal's creation.
- **Board**: `GET /pipelines/{id}/board?limit=25` answers the pipeline with, per stage in order, `count`, `amount` and `weighted` (amount times probability, rounded half up), each a `{currency: minor units}` map, `deals` (the first `limit` cards, top first) and `next_cursor`. A card is `{id, display_name, amount, close_date, owner_id, board_position, stage_id, stage_entered_at, days_in_stage, rotting, last_activity_at, values}`: `rotting` is true when `days_in_stage` is more than the stage's `rotting_days`, and `last_activity_at` is the newest entry on the deal's timeline. The next page of one column is the same call with `stage` and that stage's `next_cursor`.
- **Order inside a stage**: each deal has a `board_position`, an exact decimal sent as text, lower is higher. A new deal, or one entering a stage, lands on top. To drop a card, send its neighbours, `after_id` the card above the drop and `before_id` the card below (either or both); the deal takes the midpoint of their positions, so a drop writes one record, with no event and no new `updated_at`. `position` sets a value of your own instead. A neighbour must be another deal of the target stage (422) and they must be in order (409: reload the board).
- **Forecast**: `GET /pipelines/{id}/forecast?period=month|quarter&from=&to=` groups deals by `close_date` and answers `{periods: [{label, start, end, pipeline, best_case, commit, weighted, won, owners: [{owner_id, ...the same five}]}]}`, each metric a `{currency: minor units}` map: `pipeline` is the open deals, `best_case` those in stages of 50 % or more, `commit` those of 80 % or more, `weighted` the open deals by probability, `won` the deals in won stages. Lost deals and deals with no close date or no amount are left out; `owner_id` is null for deals nobody owns.
- **Layouts**: `GET/PUT /pipelines/{id}/layout` keeps the caller's own `{collapsed: [stage ids], card_fields: [field keys]}` (default: nothing collapsed; `amount`, `close_date`, `owner_id`). Nobody else can read it, in SQL too.
- **Screens** (`frontend/src/pipeline`): `/pipeline` is the board of the last pipeline you used and `/pipeline/:id/forecast` its forecast; `/settings/pipelines` edits pipelines and stages. The board has no server side filter yet, so its quick filters (my deals, close date, search) work on the cards loaded on the device and say so. A card moves by drag and drop, by its "Move to stage" menu (`M` on a focused card) or by `Shift` and the arrow keys; a move the stage refuses opens a small dialog with the fields it wants, and a lost stage asks for the reason. What the UI shows follows the role in `/api/me` (a Viewer cannot drag, a role without `pipelines.manage` sees the settings read only), and the server still has the last word: a 403 is shown with its message and the board turns read only. The public demo (`VITE_DEMO=1`) runs the same screens on `src/pipeline/memoryClient.ts`, which keeps pipelines, positions, exit rules and the forecast in memory on top of the demo records.

## Roles, permissions and audit

Two layers (ADR 0004). Row level security keeps tenants apart; `app/permissions.py` decides what a user may do inside a workspace: which actions, which records, which fields. Workflows and AI tools, when they arrive, go through the same functions as a named actor with a role (the `Automation` system role by default), never as a superuser.

- **Roles** belong to the organization, so an agency defines "Account manager" once and uses it in every client workspace. Sign up seeds the system roles (`app/roles_seed.py`): **Owner** (everything), **Admin** (everything but billing), **Manager**, **Member** (what a member could always do), **Viewer** (reads, changes nothing) and **Automation**. Owner and Admin are locked and are what org owners and admins hold in every workspace; the others can be edited, and no system role can be deleted. A user's role is set per workspace: `PUT /api/v1/members/{user_id}` with `{"role_id"}` (`members.manage`; it also adds an org member to the workspace, and unless you are an org owner or admin you cannot hand out a role that can do more than yours). `GET /api/v1/members` lists the people who can act there. `GET/POST /api/v1/roles` and `GET/PATCH/DELETE /api/v1/roles/{id}`: a custom role starts as a copy (`{"name", "copy_from": "<role key>"}`), `PATCH` replaces `capabilities` and `object_rules`, and a role someone still holds cannot be deleted. Creating, changing and deleting roles needs an organization owner or admin as well as `roles.manage`, because a change reaches every workspace of the org; it applies on the next request of everyone who holds the role.
- **Capabilities** are plain strings, listed in one place, `permissions.CATALOG` (module, capability, description); a role that names an unknown one is a 422. `contacts`, `companies`, `deals` and `records` (custom objects) each have `.read`, `.write`, `.delete` (also the trash and restore) and `.export`; then `schema.read` (objects, fields, association types, tags, views), `objects.manage` (objects and association types), `fields.manage`, `tags.write` (create and apply), `tags.manage` (rename, merge, delete), `views.write`, `views.manage` (other people's shared views), `webhooks.manage`, `members.read`, `members.manage` (roles of members, teams, the simulator), `roles.manage`, `audit.read`, `pipelines.manage` (pipelines and stages), the six of forms (`forms.read`, `forms.write`, `forms.publish`, `forms.delete`, `responses.read`, `responses.export`), and `workflows.publish`, `messages.send` and `billing.manage` for the modules that will use them. A module that adds one lists it in the catalog and in `roles_seed.SYSTEM_ROLES`, and grants it to existing organizations in its migration.
- **Object rules** are per object key (`contact`, `deal`, a custom object) or `*` for any other, with a `scope`, `hidden_fields` and `readonly_fields`. A role with no rule for an object sees none of its records. Scopes: `all`; `own` (the record's owner is the user, or one of its `user` fields names them: an assignee); `own_and_unassigned` (own, and records with no owner); `team` (own, and records owned by anyone in the user's teams or the teams below them); `none`. Without the `.read` capability for an object's kind, the scope is `none`. A record the scope does not show is a **404 everywhere**, never a 403: reads, lists, counts, search (`q`), saved views and their counts, `include=` expansion, filters through associations (`company.name`), the trash, tag counts and the timeline, so its existence does not leak (a link to it is left out of the timeline of a record the user can see). A record created by someone whose scope would hide it, with no `owner_id` sent, is owned by its creator; send `"owner_id": null` for an unassigned one.
- **Hidden fields** are never returned, and for that role they are not fields at all: they are missing from the object's field list, a filter or sort that names one is a 400 `unknown field` (`filter.field`), a write that names one is a 422 `is not a field of contact`, and `q` does not search their values (a role that hides fields searches without the index, see `query.search_vector`). When a hidden field is part of a record's display name (a primary field, or the email or phone it falls back to), the name is rebuilt from the fields the role can read (`(hidden)` if none), and `display_name` cannot be searched, sorted or filtered on either. Saved views that use a hidden field do not exist for that role. A **read-only** field is returned, and a write to it is a 403 with `fields` naming it (`values.lifecycle`). Timeline and audit events carry a record's values, so they are served without the fields the role hides. A field a role cannot write but that is `required` makes creating that kind of record fail for it, so do not hide or lock required fields.
- **Enforcement** is declared by the route and applied again where the data is. Each route takes a dependency from `app.permissions`: `requires("fields.manage")`, `requires_object("write")` for `/objects/{key}/...`, `requires_trash("delete")` for `?object=`, `requires_records("read")` for `/records/{id}/...` (which turns away roles that could not do it on any kind of record; the precise check comes after the record is found, so a record out of scope is a 404 first). The 403 reads `Your role does not allow this: it needs the capability contacts.write`. `tests/test_permissions.py` walks every `/api/v1` route and fails on one that declares no capability, with an allowlist (`PUBLIC`) for routes that really are public, and calls each route as a Viewer to check it is refused exactly where it says. The record engine does the rest (`store.create` and `update` run `check_write`, `trash` and `restore` need `.delete`, every query starts from `store.live`). New code that reads records should use those, not a raw `Record` query, and anything that shows a record's content should go through `permissions.redact` (or `redact_event`). What a request works out (role, rules, teams) is cached in `ctx.cache` for that request only.
- **Teams**: `GET/POST /api/v1/teams`, `GET/PATCH/DELETE /api/v1/teams/{id}`, `PUT` and `DELETE /api/v1/teams/{id}/members/{user_id}`. A team may sit under another (`parent_team_id`, no cycles); deleting one moves its sub-teams up. Reading is `members.read`, changing is `members.manage`. The team scope is the filter node `{"team": [team ids]}` (the record's owner is in one of them), which any filter may use.
- **My capabilities**: `GET /api/v1/me/capabilities` (needs only a workspace the caller can act in) answers `{role, capabilities, teams, objects}` for the caller: the capability strings of the catalog, and per object its `scope`, `hidden_fields`, `readonly_fields` and what the role `can` do (`read`, `write`, `delete`, `export`). It is the summary the simulator gives for any user, taken for the caller, so the two cannot disagree. `/api/me` is not workspace scoped (one user, a role in each workspace), which is why this lives under `/api/v1` with `X-Workspace-Id`. The web app reads it once per workspace (`lib/capabilities.ts`): `can("channels.manage")` decides what a screen OFFERS, and a screen never guesses from a role's name (the server still decides what is ALLOWED). Until the answer arrives `can` says yes, and screens that must not show anything before they know read `ready`.
- **Catalog**: `GET /api/v1/permissions/catalog` (`members.read`) lists every capability with its module and description, and the scopes, for the role editor.
- **Simulator**: `GET /api/v1/permissions/explain?user_id=&record_id=` (`members.manage`) answers with the user's role, capabilities, the rule per object (scope, hidden and read-only fields, what they can do) and teams, and for a record whether they see it and why, for example `visible: owner is in team East, scope team`. It runs the same functions enforcement does, on a copy of the request with that user swapped in, so the two cannot drift; the tests compare it with the API on a matrix of users and records.
- **Screens** (`frontend/src/admin`): Settings > Team and roles (`/settings/team`: members and their roles, the roles with the capability matrix, scopes and the field matrix, teams and sub-teams, the access check) and Settings > Audit log (`/settings/audit`). They follow the role in `/api/v1/me/capabilities` and show the server's refusals; the public demo has no data for them.
- **Audit log** is the event log (ADR 0003): every write already emits an event in its own transaction, and request handlers can only add to `events` (INSERT and SELECT, no UPDATE, DELETE or TRUNCATE). Configuration writes emit `object.*`, `field.*`, `association_type.*`, `pipeline.*`, `stage.*`, `stages.reordered`, `role.*`, `team.*`, `member.role_changed` and `webhook_endpoint.updated` and `.deleted` (the URL is not in the event, only `url_changed`); a change that changes nothing emits nothing. Security events are written to every workspace the user can act in: `user.password_changed` and `auth.sessions_revoked` (with a `count` and a `reason`). Saved views are the user's own preferences and are not audited. `GET /api/v1/audit` (`audit.read`) filters by `actor`, `subject` (a record id: its events, and the links that touch it), `type` (`record.updated`, or `record.*`) and `from` and `to` (inclusive), newest first with a cursor, and `GET /api/v1/audit/export` is the same as CSV (up to 50 000 events) and is itself an `audit.exported` event; `GET /api/v1/audit/event-types` lists the types for the filter. `audit.read` shows the events of every record whatever a role's scope says; the fields a role hides are still taken out.

## Tasks and notifications

Tasks (module 11) are to-dos with a due date, an assignee, a priority, notes, an optional link to any record, a repeat rule and an optional task they wait for. Roles hold three capabilities for them, `tasks.read`, `tasks.write` and `tasks.delete` (Members and Managers all three, Viewers read, Automation reads and writes), and a task shows the name of its record only to someone who may see that record (`record` is null otherwise). Notifications and their settings belong to the person, so they need no capability.

- **Tasks**: `GET/POST /tasks`, `GET/PATCH/DELETE /tasks/{id}`, `POST /tasks/{id}/complete` and `/reopen`, `POST /tasks/bulk` (`{"ids": [...], "action": "complete" | "assign", "assignee_id"}`, up to 200; a task whose dependency is open is `skipped` with the reason) and `POST /tasks/{id}/reorder` (`{"before_id"}`: the manual order is a float `position`). A list is in manual order with a cursor and the filters `assignee` (`me`, `anyone`, `unassigned` or a user id), `status`, `due` (`overdue`, `today`, `upcoming`, `none`), `due_after` and `due_before` (a calendar), `completed_after` and `record_id`. The reader's zone comes from `tz` (an IANA name, UTC when absent), because "today" depends on it: a timed task is overdue once its time has passed, an all-day task (`all_day`, due on a date, kept as midnight UTC of it) once its date has. The assignee pickers read the people of the workspace from `GET /members`.
- **Repeats**: `recurrence` is the part of RRULE people use: `FREQ=DAILY|WEEKLY|MONTHLY`, `INTERVAL`, `BYDAY` (weekly), `BYMONTHDAY` (monthly, `-1` is the last day) and `COUNT` or `UNTIL`, stored in one canonical form. Completing a recurring task creates the next one in the same transaction (`next` in the response and `next_task_id` in `task.completed`). A timed task keeps its wall clock in the `tz` of the request, an all-day one moves by dates, and a short month clamps (the 31st becomes the 28th, and the next one is the 31st again). The tasks of a series point at the first (`parent_task_id`), which is how `COUNT` is counted. A repeating task needs a due date.
- **Dependencies**: `depends_on_task_id`. Completing a task whose dependency is open is a 409 `task_blocked` that names it, a cycle is a 422, and deleting a task frees the ones that waited for it.
- **My Day**: `GET /my-day?tz=` answers `{"date", "timezone", "tasks": {"overdue", "today", "counts"}}`. A module adds a section with `@tasks.day.section("name")` (a function of the request and the zone) and the response gets one key for it, so appointments and assigned conversations join when they exist.
- **Notifications** are made from events by a consumer in the worker (`app/notifications/consumer.py`, started from the end of the log when migration 0009 runs): a task assigned to you (`task_assigned`, from `task.created` and `task.updated`), a task due (`task_due`, from a `task.due` job that waits for the due time and does nothing for a task that was finished, moved or reassigned meanwhile) and a record assigned to you (`record_assigned`, an `owner_id` set to you). Nobody is told about what they did themselves, and each is made once per event or due time. Each person has a rule per kind (`GET/PUT /notifications/prefs`): the `in_app` channel on or off, and a scope, `mine` (what concerns you) or `all` (everything of that kind in the workspace). Quiet hours (`quiet_start`, `quiet_end`, `tz`) hold a notification until they end: it is dated then, and not listed or counted before. `email` and `digest` are stored for the email module; nothing is sent by email yet. The bell reads `GET /notifications` (cursor, `unread=true`), `GET /notifications/unread-count` and `POST /notifications/read` (`{"ids": [...]}` or `{"all": true}`). Row level security shows a notification and a preference to their user only, and the API role may only set `read_at`.
- **Web app**: My Day (`/my-day`) is where signing in lands (`/` redirects there; a demo build with `VITE_DEMO=1` opens on contacts). Tasks (`g t`) has a list grouped by Overdue, Today, Upcoming and No date with a quick add that reads "Call Ada tomorrow at 3pm" (`lib/dates.ts`), a board by status (To do, Blocked, Done) and a month calendar. `j` and `k` move, `x` completes, `e` edits and `n` adds, and completing offers an undo. The bell polls every 60 seconds (the SSE stream belongs to the inbox screen, see Inbox and channels) and Settings > Notifications holds the rules.

## Inbox and channels

One conversation per contact with every channel in it (ADR 0005, modules 12 to 14). Everything is under `/api/v1`, uses the conventions above and the `X-Workspace-Id` header, except the public webhook and chat endpoints. Sending, snooze wake-ups and the realtime stream need the worker (`python -m app.worker`). Code is in `backend/app/inbox/`; the provider adapters stay in `app/channels/`.

- **Channels** (`/api/v1/channels`): workspace admins create, edit, disable and test them; every member lists them to pick a sender (members see no settings). `POST` takes `kind` (`sms`, `email`, `webchat`, `whatsapp`), `provider`, `name`, `address`, `config` and `secrets`:

  | provider | kind | `address` | `config` | `secrets` |
  | --- | --- | --- | --- | --- |
  | `twilio` | sms | sending number (or a messaging service SID in `config`) | `account_sid`, `messaging_service_sid` | `auth_token` |
  | `telnyx` | sms | sending number | `public_key`, `messaging_profile_id` | `api_key` |
  | `smtp`, `ses` | email | From address | `host`, `port`, `security`, `username`, `message_id_domain` | `password` |
  | `mailgun` | email | From address | `domain`, `region`, `message_id_domain` | `api_key`, `signing_key` |
  | `meta` | whatsapp | business number | `phone_number_id` | `access_token`, `app_secret`, `verify_token` |
  | `internal` | webchat | a generated widget key | `title`, `greeting`, `color` | none |

  Any channel also takes `segment_cost` (price of one SMS segment, default 0), `quiet_start` and `quiet_end` (`"21:00"` and `"08:00"`; equal times switch quiet hours off), `frequency_cap` (`{"max": 10, "hours": 24}`; SMS and WhatsApp default to 10 a day, email to none, `max` 0 to none), `auto_replies` (`{"stop": "...", "start": "...", "help": "..."}`, an empty text switches one off) and `reply_to` (email). An unknown setting is a 422, so a secret cannot end up in `config`. **Secrets are write-only**: no response, event, job or log carries one, and `secrets_set` says whether the channel has any. `PATCH` merges `config` and `secrets` (a null removes a key) and takes `name`, `address` and `status` (`disabled` or `active`); `POST /{id}/test` asks the provider to accept the saved credentials where its adapter can (Twilio, Telnyx, Mailgun and WhatsApp read the account; SMTP logs in without sending) and answers `{"ok": true, "detail": "..."}`, moving the channel between `active` and `failing` (`status_detail` says why); `POST /{id}/estimate` takes `{"body": "..."}` and answers `{encoding, segments, chars, estimated_cost}` for the composer. For admins a channel shows `webhook_url`, the URL to paste into the provider's console (the first `PUBLIC_URL` origin plus `/api/hooks/<provider>/<channel id>`); a webchat channel shows `widget_key` and the `embed` snippet. A new channel is `pending` (webchat: `active`) until a test, a signed webhook or an accepted send proves it works; only `disabled` stops it.
- **Inbound** (`POST /api/hooks/{provider}/{channel_id}`, public, and Meta's `GET` handshake): the channel is loaded in the system scope, the adapter verifies the signature on the raw body (401 and a log line for anything unsigned, wrongly signed or stale; an SMTP channel has no webhook, so every call is refused), and only then does the request move into the channel's workspace. Each message finds its contact by `phone_e164` or `email_norm` through the record store (a new one is created by the platform, with no actor), takes the next `seq` of the contact's conversation under its row lock, reopens a closed or snoozed conversation and emits `message.received`. A retried webhook changes nothing: a message is stored once per `(channel, provider message id)`, even when two copies arrive at the same time. An email from an address nobody knows that answers one of our messages (`In-Reply-To`) joins the conversation of that message instead of making a new contact. A sender that cannot be a contact (an alphanumeric sender id) is logged and acknowledged. Delivery reports move an outbound message forward only (`queued`, `sent`, `failed`, `delivered`, `read` in that order, so a late `sent` never undoes `delivered`) and emit `message.status_changed`; an email complaint or unsubscribe is an opt-out. On SMS and WhatsApp a message that is only STOP, START or HELP (`compliance.keyword`) never reaches the inbox: it is kept in the thread as a system line that neither reopens nor marks unread, STOP and START set the contact's consent for that channel kind, and the channel's auto reply is sent once.
- **Replying** (`POST /conversations/{id}/messages`: `body`, `kind` `message` or `note`, `channel_id` (default: the channel the conversation last used), `subject` and `html` (email), `attachments` (URLs)): `compliance.can_send` runs first and a refusal is a 422 whose error `code` names the reason (`opted_out`, `dnd`, `quiet_hours`, `frequency_cap`, `no_address`, `no_channel`, `channel_disabled`), `message` is the sentence to show ("Opted out by STOP on Oct 3") and `fields.retry_at` says when waiting helps. Quiet hours apply to SMS and WhatsApp in the contact's time zone (their `timezone` value if the workspace has that field, else the zones their number can be in; several zones wait for the latest end), except for a contact who wrote in the last 24 hours. Otherwise the message is stored as `queued` in the request's transaction with a `message.send` job, and the response carries the message plus, for SMS, `estimate` (segments, encoding, estimated cost; `segments` and `estimated_cost` are on the message too). The job checks consent again, calls the adapter with the message id as idempotency key (a message that already has a provider id is never sent again), records the provider id and `sent`, or retries a retryable error with the queue's backoff (up to 6 attempts, `error` shows the last one) and marks a permanent one `failed`; it emits `message.sent` and `message.failed`. An email reply threads (`In-Reply-To` and `References` from the conversation) and gets `Re: <subject>`. A webchat reply is `sent` at once. A note is never sent and moves nothing in the list. Send an `Idempotency-Key` from the composer.
- **The inbox**: `GET /conversations?view=&channel_id=&q=&limit=&cursor=` with `view` one of `open` (default), `mine`, `unassigned`, `snoozed`, `closed` or `unread` (not closed, with a message the caller has not read), `channel_id` for conversations whose last message used that channel, and `q` for words matched as prefixes in message text and the contact's name, email and phone. It pages by `last_message_at` with a signed cursor, and the first page carries `counts` for every view and `channels` (open conversations per channel) in the same answer. A row is `{id, contact: {id, display_name, email, phone}, status, assignee_id, team_id, snooze_until, last_message_at, last_inbound_at, channel_id, channel_kind, preview, last_direction, unread, last_seq, visitor, created_at}`. `GET /conversations/{id}` adds `last_read_seq` and `messages` (newest first, 50, `next_cursor` to page back by `seq`); `GET /conversations/{id}/messages?q=&limit=&cursor=` pages and searches inside one conversation. A message is `{id, conversation_id, seq, direction, channel_id, kind, subject, body, html, attachments, status, error, provider_message_id, thread_ref, sent_by, occurred_at, created_at, segments, estimated_cost}`; show `occurred_at`, order by `seq`, and sanitize `html` (it is whatever the sender mailed). `POST /conversations` `{contact_id}` returns the contact's conversation (201 new, 200 existing). Actions: `POST /{id}/assign` (`user_id` of a workspace member and/or `team_id`, null unassigns, a missing key stays), `/snooze` (`until`, an aware time within a year; it comes back as open by itself, or when the contact writes), `/close`, `/reopen`, `/read` (`seq`, default all; the mark only moves forward and is per user) and `/unread` (the way back: the caller's mark goes to just before the contact's last message, so it counts as unread again; nothing happens for a conversation the contact never wrote in). `PATCH /{id}/messages/{message id}` edits a note, for its author only. Each change emits `conversation.updated` with `changes`. Conversations belong to a contact and show only while the caller may see the contact (the record scope hook of ADR 0004); a conversation of a trashed contact is hidden until the contact is restored.
- **Consent**: `GET /contacts/{id}/consents` lists the contact's marks per channel kind (`opted_out`, `opted_in`, `dnd`, with `source` and time); `PUT /contacts/{id}/consents/{kind}` with `{"dnd": true|false}` switches do not disturb. Staff cannot undo an opt-out (409): only the contact's own START does. Changes emit `consent.changed`.
- **Realtime** (`GET /api/v1/stream`, Server-Sent Events, also `?workspace_id=` because EventSource cannot set headers): an events consumer in the worker `NOTIFY`s `gohigh_events` with `{id, type, workspace_id, ids}` for every `message.*`, `conversation.*` and `record.*` event, every API process holds one `LISTEN` connection (started in the lifespan) and fans payloads out to the streams of that workspace. Payloads carry ids only (`message_id`, `conversation_id`, `contact_id`, `record_id`, `object`): refetch through the API, so permissions apply. Read it with `new EventSource(url)` and `JSON.parse(event.data)`; there are no named events. A stream pings every 25 seconds, ends after 30 minutes (the browser reconnects and the session is checked again), and a reconnect resumes from `Last-Event-ID` while that event is in the process's last 1000; otherwise (or after a database reconnect, or if the client falls too far behind) it sends `{"type": "stream.resync"}` and the client refetches what it shows.
- **Webchat**: paste `<script src="https://HOST/widget.js" data-key="WIDGET KEY" async></script>` (optionally `data-color="#2563eb"`). The 9 KB script has no framework, draws a bubble at once, builds the panel on the first click, keeps its token in this page's `localStorage` (every access guarded) and polls while open. It uses `/api/public/chat/{widget_key}`: `POST /session` (a signed visitor token plus `title`, `greeting`, `color`; stores nothing), `POST /messages` (`body` up to 2000 characters, `client_id` so a retry is stored once; the first message makes the contact "Visitor 1a2b" and the conversation), `POST /identify` (`name`, `email`, `phone` on the visitor's contact; separate records are not merged yet) and `GET /messages?after=<seq>` (their messages and the replies, never notes). Tokens go in `Authorization: Bearer`, are signed with `SECRET_KEY` for one widget and 30 days, and any origin may call (CORS `*`, no cookies). `CHAT_SEND_PER_IP` (10), `CHAT_SEND_PER_KEY` (300), `CHAT_POLL_PER_IP` (120) and `CHAT_POLL_PER_KEY` (6000) are requests per minute counted in Postgres (`chat_limits`); past them the answer is 429 with `Retry-After`. A filled-in hidden `website` field is dropped silently.
- **Web app**: the Inbox (`/inbox`, `g i`) has three panes: the views (Open, Mine, Unassigned, Unread, Snoozed, Closed and one per channel, each with its live count), the conversation list (a screenful of rows at a time, paged by cursor, with the contact, channel, preview, time, unread dot and assignee) and the thread, with the contact card beside it. The thread groups messages by day in the order of `seq`, marks the channel and delivery state of each message (sending, sent, delivered, read, failed with Retry), draws internal notes in their own colour (the author edits them) and shows an email in a sandboxed frame with no scripts and no remote images until "Show images" is pressed. The composer picks only channels the contact can be reached on, shows the segment count and price of an SMS while typing, takes a subject and simple formatting for email, and sends with `Ctrl/Cmd+Enter` and an `Idempotency-Key`; a message shows at once and settles when the server answers, a refusal (`opted_out`, `dnd`, `quiet_hours` with the time it resumes, `frequency_cap`, `no_address`, `no_channel`, `channel_disabled`) is an inline banner in the server's words and the text stays in the box. Keys: `j` `k` `Enter` `o` `e` `s` `a` `r` `n` `u` `/` `f` `i` and `g i`, all in the `?` sheet. It listens to `/api/v1/stream` while open (reconnecting with a growing pause, and reading everything again after `stream.resync`), refetching only the rows, counts and open thread that an event names. The unread count is in the tab title and on the sidebar. Settings > Channels (`channels.manage`) lists the channels, adds Twilio, Telnyx, SMTP, Mailgun, WhatsApp and web chat accounts with write-only secrets, tests the connection and shows the webhook URL or the embed snippet to copy; a contact record has a Message action. The public demo (`VITE_DEMO=1`) answers all of this from memory with about 40 fictional conversations. Code is in `frontend/src/inbox/`.
- **Events**: `message.received`, `message.queued`, `message.sent`, `message.failed`, `message.status_changed`, `message.note_added`, `message.updated`, `conversation.created`, `conversation.updated`, `channel.created`, `channel.updated` and `consent.changed`; their schemas are in `backend/app/event_types/`.
- **Settings and secrets**: provider secrets are encrypted with AES-256-GCM under a key derived from `SECRET_KEY` (HKDF-SHA256) and bound to their row, so set the same `SECRET_KEY` on every replica and the worker, and never change it without re-encrypting (a changed key makes every stored secret unreadable). The API role can write the `secrets` table but cannot read its ciphertext column; only the worker and the verify, send and test code decrypt, on the owner role.

## Forms, surveys and quizzes

One engine for all three (module 17). A form is a row in `forms` with immutable `form_versions`: saving the builder's draft adds a version, publishing makes one of them what visitors see, and a response keeps the version it began on, so editing a live form never changes a half finished answer. The admin API is `/api/v1/forms` (guarded by the forms capabilities below; the usual envelope, cursors and idempotency keys), the public runtime is `/api/public/forms/{public_key}`, and the web app has a Forms area (switch it on or off under Apps; it is on by default).

- **Capabilities** (ADR 0004): `forms.read` (forms, versions, analytics), `forms.write` (create, edit, save drafts, duplicate), `forms.publish` (publish, close, reopen, take offline, and change the settings of a form that is live), `forms.delete` (trash and restore), `responses.read` and `responses.export` (the CSV). Owner, Admin and Manager hold all six; Member holds `forms.read`, `forms.write` and `responses.read`, so it drafts and reads but does not publish; Viewer holds `forms.read` and `responses.read`; Automation holds none. Migration 0010 grants them to the system roles of existing organizations. A response shows the viewer only what their record permissions allow of its contact: answers that fill a contact field the role cannot read are left out, the id of a contact outside the role's scope is not shown, and the `form.submitted` event on a timeline carries no answers for the viewer.
- **Admin API**: `GET/POST /forms` (`status`, `kind`, `q`, `trashed`; each row has `responses`, `starts` and `completion_rate`), `GET/PATCH/DELETE /forms/{id}` (DELETE moves it to the trash, `POST /forms/{id}/restore` brings it back), `POST /forms/{id}/duplicate`, `GET/POST /forms/{id}/versions` (saving what the newest version already holds changes nothing), `GET /forms/{id}/versions/{version_id}`, `POST /forms/{id}/publish` (the newest version, or `{"version_id": ...}`; also reopens a closed form), `PATCH {"status": "closed"|"draft"}` to stop taking responses or take the form offline, `GET /forms/{id}/submissions` (`status`, `from`, `to`, cursor), `GET /forms/{id}/submissions/{sid}`, `GET /forms/{id}/submissions/export.csv` and `GET /forms/{id}/analytics?from=&to=`. Events: `form.created`, `form.updated`, `form.published`, `form.deleted`, `form.restored` and `form.submitted`.
- **The definition** is JSON checked when a version is saved: `steps` of `fields` (`short_text`, `long_text`, `email`, `phone`, `number`, `select`, `multi_select`, `checkbox`, `date`, `rating` 1 to 5, `yes_no`, `hidden` filled from a URL parameter, `consent` with its text, and the content blocks `heading` and `paragraph`), each with `required`, `validation`, `options`, and `maps_to`, the key of a contact field it fills (the field must exist, not be computed, and be of a compatible type). Answers are validated by the record engine's own field types. Keys of steps and fields share one namespace.
- **Logic** is a list of rules `{"when": condition, "do": show|hide|jump|end, "target", "from"}`. A condition is the filter language of ADR 0002 over earlier answers (`and`, `or`, `not`, `{"field", "op", "value"}` with `is`, `is_not`, `contains`, `in`, `not_in`, `gt`, `gte`, `lt`, `lte`, `is_empty`, `is_not_empty`, each only for the types it makes sense for). A rule may only look at questions that come before what it controls, a jump goes to a later step, and an end rule finishes the form after its step, so loops and dangling references are refused with a path (`definition.logic.0.when.field`). The server walks the same logic on completion: hidden questions and skipped steps are not required and their answers are dropped. `app/forms/logic.py` and `frontend/src/forms-runtime/logic.ts` are the same algorithm; `backend/tests/fixtures/form_logic.json` holds the cases both test suites must agree on.
- **Quizzes** (`kind: quiz`): a scored question has `{"quiz": {"correct": ..., "points": n}}` (select, multi select as an exact set, yes or no, rating, number, short text with any of several accepted answers) and the definition has `quiz: {"pass_mark": percent, "bands": [{"min": percent, "title", "message"}]}`. Completing returns `result` (`score`, `max_score`, `percent`, `passed`, `band`, and which questions were right) and stores `score`; only questions the visitor was shown count, and the arithmetic is integer so the browser agrees. The public definition never contains right answers.
- **Public runtime**: `GET /api/public/forms/{key}` (the published definition without mapping or scoring, `410 form_closed` once closed, by date or by response limit), `POST .../views` (counts a view, returns a signed `view_token`), `POST .../submissions` (starts a response or, with `resume_token`, saves the answers so far; nothing is validated yet; the resume token is returned once), `POST .../resume` (the saved answers and the version the response began on) and `POST .../submissions/{id}/complete`. Completing twice is harmless: the second call answers like the first. Every public answer is sent with `Cache-Control: no-store`, any origin may call these endpoints (CORS) and none sends credentials.
- **Contacts**: a completed response finds the contact with the same email or phone (the oldest, among duplicates) or creates one, through the record store, so validation, display names and `record.created` and `record.updated` events are the usual. An empty answer never clears a field. `settings.contact.existing` is `fill_empty` (the default: only fields the contact has no value for, which stops a stranger's answer from rewriting what you know) or `update` (a new answer overwrites; opt in per form); `settings.contact.create: false` leaves contacts alone. A contact the form creates gets `source = form` when the workspace's contact object has a `source` select field with a `form` choice; a contact that already existed never has its source touched. The contact is written as the organization's Automation role (a response has no signed-in user), so an organization that takes `contacts.write` away from that role stops forms from writing contacts: the response is kept with a `contact_error`. If the CRM refuses the contact (a required field the form does not ask for), the response is still kept and says why (`contact_error`). The `form.submitted` event carries the answers, the score and the contact id, and shows on the contact's timeline, so webhooks and workflows can use it. Consent boxes are stored as evidence of opt-in: the words shown, the time, the form and a keyed hash of the visitor's address.
- **Settings** (`PATCH /forms/{id}` with `settings`): `success_message`, `redirect_url` (http or https only), `closed_message`, `notify_emails` (logged until the email module exists), `double_submission` (`allow` or `block` a contact that already answered), `close_at`, `max_responses`, `spam_protection`, `rate_limit_per_minute` and `max_body_kb`.
- **Spam protection** is on by default: a hidden honeypot field (a bot is told it worked and nothing is stored), a minimum fill time measured from the signed view token (`FORM_MIN_FILL_SECONDS`, default 3), and always a rate limit per form and visitor (a Postgres counter per minute, keyed by a hash of the address) and a size limit per form.
- **Hosted page and embed**: `/f/{public_key}` is a small HTML shell (with a strict Content-Security-Policy) that loads the runtime; `?theme=dark` picks the dark theme. To embed, paste `<script src="https://your-host/embed.js" data-form="PUBLIC_KEY" async></script>` where the form should appear: it draws into a shadow root next to the tag (no iframe), so the page's CSS and analytics are untouched, and it loads the published version each time. `data-theme` (`light`, `dark`, `auto`), `data-target` (a selector) and the host's `--gh-accent`, `--gh-radius` and `--gh-font` variables adjust it. The runtime (`frontend/src/forms-runtime`, plain TypeScript, about 8 KB gzipped) is a separate build, `npm run build` writes it to `dist/embed.js`. It saves partial answers as people type, offers a link to carry on later (`?gh_resume=`), redirects or shows the result page, and mirrors the server's logic.
- **Builder**: the question list with a palette, drag or keyboard reordering (Alt and the arrow keys), undo (Ctrl or Cmd+Z, a deleted question comes back), steps, a settings panel per question (options, validation, contact mapping, quiz scoring), a flow map of steps, jumps and early ends with an editable rules list, a live preview that is the real runtime, a publish flow that gives the link and the embed code, a responses table with a detail sheet and CSV export, and analytics: views, starts, completions, completion rate, time to complete, and where people leave per step and per question.
- **CSV export** neutralizes spreadsheet formulas: text that starts with `=`, `+`, `-`, `@`, a tab or a line break gets a leading apostrophe (numbers are left alone), in headers and cells alike; choices are written by label, one column per question of any version, up to 50 000 responses (`X-Export-Truncated` says when there were more).

## Calendars and booking

Module 16 (`app/calendars/`). Admin routes are under `/api/v1`: reading is `calendars.read`, cancelling, moving and marking bookings and keeping your own hours is `calendars.write`, creating and changing calendars, hosts and resources and other people's hours is `calendars.manage` (Manager and above; Members get read and write, Viewers read). Visitors use `/api/public` and the pages `/book/{workspace_slug}/{calendar_slug}` and `/booking/{token}`; a workspace's handle (`workspaces.slug`, `acme-4f2a`, made from the organization name when it is created) is in the link.

- **Calendars** have a `kind` (`personal`, `round_robin`, `collective`, `class`, `service`), one to three meeting lengths, buffers before and after, minimum notice, a booking window in days, a start-time interval, a limit per day, seats (class), a time zone, locations (`phone`, `video` link, `in_person`, `custom`), questions (name and email are always asked, phone can be optional, up to ten text, long text or select questions of your own), `confirmation` (`auto`: a booking is `confirmed`; `manual`: it is `booked` until `POST /bookings/{id}/status {"status": "confirmed"}`), reminder offsets, a cancel and reschedule cutoff and a `status` (`active`, `paused`, `archived`). `GET/POST /calendars`, `GET/PATCH/DELETE /calendars/{id}` (a calendar with bookings is archived, 200, otherwise deleted, 204), `PUT /calendars/{id}/hosts` (a list of `{user_id, weight, priority, daily_cap, active}`; a new host without hours gets Monday to Friday 9 to 5 in the calendar's zone) and `PUT /calendars/{id}/resources` (`[{resource_id, quantity}]`). `GET/POST /resources`, `PATCH/DELETE /resources/{id}` are rooms and equipment with a quantity.
- **Hours** are `GET/PUT /availability/users/{id}` and `/availability/resources/{id}`: a week (`{"mon": [["09:00", "17:00"]], ...}`) read in the person's own time zone, plus `PUT/DELETE .../overrides/{YYYY-MM-DD}` for a day off (`{"hours": []}`) or short hours. A person with no hours is never offered. `POST /availability/busy` takes outside busy time for a person (`{"source", "blocks": [{start, end, external_id?}], "replace_from"?, "replace_to"?}`) and sets the sync health that `GET /availability/users/{id}` reports (`none`, `ok`, `stale` after a day, `error`).
- **The availability engine** (`slots.py`) turns all of that into open start times: each host's hours in their own zone (zoneinfo, so a daylight saving change moves the hours and not the clock), date overrides, bookings and their buffers (the gap between two meetings is the larger buffer, not the sum), busy blocks, minimum notice, the window, the limit per day and per host, resource capacity and, for a collective calendar, only times when every host is free. Start times are on a grid counted from midnight in the calendar's zone, in real minutes, so a 25 hour day has its 25th hour. `GET /calendars/{id}/slots?from=&to=&tz=&duration=` lists open times by day (UTC instants, grouped by the day on the visitor's clock, at most 62 days); `GET /calendars/{id}/explain?start=&tz=&duration=` says for any time whether it is offered and, if not, why, per host ("Outside Theo's hours (works 09:00 to 17:00 on Tuesday, America/New_York)", "Buffer after the 10:00 booking", "Theo has a booking from 10:00 to 10:30", "Room 1 capacity reached (1 of 1 in use)"), and who would get it if it is.
- **Round robin** (`routing.py`) gives a booking to the free host with the fewest bookings for their weight over a rolling 30 days (ties: higher priority, then the host added first); a host with weight 0 or paused gets none, one at their daily cap is skipped, and a host who owns the contact keeps them. `POST /calendars/{id}/simulate?n=20` plays the next `n` bookings forward and answers who gets each and why, with per host share against target share; it writes nothing.
- **Booking** (`booking.py`) re-validates the time inside the transaction after taking row locks (the calendar, its hosts' hours, the resources, in that order, hosts and resources by id), so two requests for one time cannot both win; the loser gets a 409 `slot_unavailable`. The contact is found by email, then phone, among live contacts, or created, owned by the host, through the record store as the workspace's Automation role; an existing contact is only filled in where a field is blank, never overwritten. Events: `booking.created` (also on the contact's timeline), `booking.rescheduled` (same host, same link; status `rescheduled`), `booking.cancelled`, `booking.status_changed` (`confirmed`, `showed`, `no_show`), and `calendar.*`, `resource.*`, `availability.updated`. `GET /bookings` filters by range (`from`, `to` overlap), `host_id`, `calendar_id`, `contact_id` and `status` and pages by start time; a contact is shown only if the caller may see it.
- **Public page**: a visitor reads the calendar (`GET /api/public/calendars/{ws}/{cal}`), its open times (`.../slots`) and books (`POST .../bookings`: `start`, `time_zone`, `name`, `email`, `phone`, `answers`, `location`, and the hidden `website` honeypot). They get a link with a secret, `/booking/{token}`, to see (`GET /api/public/bookings/{token}`), move (`.../reschedule`, `.../slots`), cancel (`.../cancel`) and add the booking to a calendar app (`.../ics`). The link holds the workspace in its first part and a 256 bit secret in its second; only the SHA-256 is stored. A calendar's `cutoff_hours` stops cancel and reschedule that close to the start (403 `change_closed`). Errors use the `/api/v1` envelope, and the public routes allow any origin (no cookies), which is how the widget is embedded without an iframe. The page and the widget are one small script with no framework (`frontend/src/book`, about 13 kB gzipped): a visitor picks a length, a time zone, a day and a time, fills in the calendar's questions and gets a confirmation with an "Add to calendar" `.ics` link and the manage link; on the manage link they see the booking, move it (open times from `.../slots`, the same length) or cancel it with an optional reason, and once the cutoff has passed the page says so instead of offering either. `npm run build` writes it to `frontend/dist/book/` (`page.html`, `book.js`, the Geist font); the API serves `page.html` for both page routes (with a strict CSP and no referrer, since a manage link holds a secret) and the script at `/book/book.js`, or a 404 that says to build. To put a calendar on any site:

  ```html
  <div data-go-high-booking="{workspace_slug}/{calendar_slug}"></div>
  <script async src="https://your-host/book/book.js"></script>
  ```

  The widget draws in a shadow root, so the site's CSS cannot reach it, and talks to the host the script came from. `data-theme="dark"` on the div (or an ancestor) picks the dark theme, `--gh-accent`, `--gh-radius` and `--gh-font` on the div restyle it, and its manage link opens on your host. Add `?theme=dark` to a page link for the dark theme.
- **In the app**: Calendar (`/calendar`) shows the week's bookings on your clock over your working hours (`src/calendar`), each one opening a sheet with the invitee, answers and contact, to confirm, cancel or mark showed or no-show; the Booking pages tab lists the calendars with a copy-link button. The public demo has fictional bookings for the current week.
- **Reminders**: making or moving a booking schedules one job per reminder offset (`calendars.reminder`, at `start - offset`, none for a time already past); the reminder row (`booking_reminders`, unique per booking and offset) goes from `pending` to `sent` in one UPDATE when the job runs, so a retried job records nothing twice, a job for a time the booking has left does nothing, and cancelling cancels them. It records `booking.reminder_due`; sending (inbox, workflows) is for those modules.
- **Feeds**: `POST /calendars/feed` makes your private ICS feed link (`/api/public/feeds/{token}.ics`, your bookings from 30 days ago on); the link is shown once and asking again replaces it.
- **Spam**: a filled honeypot gets a believable 201 and stores nothing; every attempt counts per calendar and visitor (a hash of the address with `SECRET_KEY`) and per calendar (`BOOKING_MAX_PER_IP` 8 and `BOOKING_MAX_PER_CALENDAR` 120 per `BOOKING_WINDOW_MINUTES` 10, a 429 with `Retry-After`).
- **Not built yet**: live sync with outside calendars (the busy import route is where it will write), recurring series (`series_id` is there), payments and packages, video links made per booking, auto status, staff-made bookings, calendar groups and rentals.


## Workflows

Module 18 (`app/workflows/`, [ADR 0006](docs/adr/0006-workflow-engine.md)). A workflow is a versioned graph that a record walks after an event; the API below is what the visual builder (a later change) will use, and a workflow saved through it is valid in the builder. Reading is `workflows.read`, editing drafts, testing, cancelling and retrying runs is `workflows.write`, and what changes what runs live (publish, pause, resume, archive, the signing secret, the settings of a live workflow) is `workflows.publish`: Members get read and write, Managers and above publish, Viewers read. Everything runs in the worker (`python -m app.worker`): enrollment is an events consumer, and a run advances by `workflow.step` jobs.

- **The graph** (`schema.py`) is `{"trigger": {"event", "object", "filter", "data"}, "start": "<node id>", "nodes": {id: node}}`. The trigger is an event about a record (`record.created`, `record.updated`, `deal.stage_changed`, `tag.added`, `form.submitted`, `booking.created`, `message.received`, `task.completed`, ... 25 today: the event types that name a record as their subject or in `contact_id` or `record_id`; `GET /workflows/catalog` lists them with their data schemas), the `object` whose records enter (default `contact`, and `deal` for `deal.stage_changed`), a filter AST over the record (ADR 0002) and `data` the event must contain (`{"form_id": "..."}`). A node is `{"type", "config", "next" | "branches"}` plus an optional `label` and `ui` for the builder: `action` (with `"action": "<key>"`), `wait`, `condition` (`config.filter`, branches `yes` and `no`), `split` (`paths` with percentages, one branch each), `goal` (`config.filter`, `otherwise` `continue` or `end`), `subflow` (saved, not yet publishable) and `end`. `next: null` or a branch to null ends the run. Node ids are `^[a-z][a-z0-9_]{0,39}$`, at most 200 nodes.
- **Validation** refuses, with an error that points into the graph (`graph.nodes.send.config.body`, the same `fields` as everywhere): an unknown node type or action, an edge to a node that is not there, a node nothing leads to (a goal needs no edge into it, runs jump to it), a loop with no wait in it, and a config its action's schema refuses. Saving also checks the graph against the workspace: the trigger object, every filter against the object's fields, an update's fields and values, tags, stages, channels (SMS, email and WhatsApp), people, an email's subject, a webhook's address (the SSRF guard), and `{{field_key}}` in text against the fields the author may read. A saved version is always valid; publishing checks it again.
- **Actions** (`actions.py`; each is a pydantic config, which is its JSON schema in the catalog, and a handler that writes through the record engine's own paths as the workspace's Automation role, so every change shows "by workflow X" in the timeline and the audit log, with `actor_type` `workflow` and the workflow's id): `record.update` (`values`, a null clears), `tag.add` and `tag.remove` (by id or name), `owner.assign` (`user_id`, or `round_robin` over a list), `deal.move_stage` (the stage's exit rules apply: a refusal fails the step with what the deal lacks), `task.create` (`title`, `notes`, `due` offset, `assignee` a user or `owner`, `priority`), `message.send` (`channel_id`, `body`, `subject`, `if_refused` `fail` or `skip`), `notify.user` (in-app, for a user or the owner) and `webhook.send` (`url`, `payload`). Text may hold `{{field_key}}` (and `{{display_name}}`); a field the author cannot read cannot be used. The Automation role's capabilities and field rules apply, so taking `tags.write` from it fails the tag steps naming it.
- **Waits** park the run (`waiting`, with `wake_at`) and schedule the wake-up with the job's `run_at`: `{"duration": {"days": 2}}` (minutes, hours, days, weeks, up to a year), `{"until_field": {"field": "renewal", "offset": {"days": -1}, "at": "09:00"}}` (a date is read at `at` in the contact's `timezone` field, else UTC; a date that has passed does not wait, an empty one fails the step), or `{"event": {"event": "tag.added", "match": {"name": "replied"}, "timeout": {"days": 3}}}` with branches `event` and `timeout`: the consumer resolves it from the events that follow the wait. A goal's condition is checked on every event of the record, and a run that meets it jumps there, once per goal. A message in quiet hours (the contact's time zone, the channel's window) is put off to the end of the window, not failed; any other refusal (opt-out, do not disturb, frequency cap, no address) fails the step with the reason, or is skipped with `if_refused: skip`.
- **Enrollment** (`enroll.py`) is an events consumer like the webhook fan-out. For each event about a record it resolves event waits, jumps goals, then judges every published workflow of that trigger (object, data, filter, and the record as it is when the event is read) and starts a run. Every check is a `workflow_trigger_checks` row kept 7 days, hits and misses, with the failing clause in words (`Lifecycle stage is "lead" did not hold (it is "customer")`). Only events after a workflow first went live count; a paused workflow takes no part; a workflow's own changes never start it; a broken filter is a logged miss, never an error that would stop the consumer. `settings.reentry` (default off) decides whether a record may enter again after its run ended; a record is never in a workflow twice at once (an advisory lock per workflow and record, and a unique index on live runs under it).
- **Runs** advance one step per transaction and write `workflow_steps` (status, `input` what it was asked, `output` what it did, `error`): `GET /workflows/runs?workflow_id=&status=&record_id=`, `GET /workflows/runs/{id}` (the trace, what it waits for, the webhooks it queued), `POST .../cancel`, `POST .../retry` (a failed run stops at its step until a person retries it; nothing retries silently). A run is shown only while its record is in the caller's scope (a 404 otherwise), and a role that hides fields gets the trace without `input` and `output`. Guards: 500 steps per run (the loop guard), and at most `WORKFLOW_CONCURRENCY` (8) steps at once per workspace; a step that finds no free slot puts its job back a few seconds later.
- **Exactly once**: a job carries the step count of the run when it was scheduled and does nothing if the run has moved on, so a job that runs twice is harmless. What leaves the system is an outbox row with the idempotency key `run:node` (`run:node:2` on the second loop round): `message.send` queues a message with `messages.idempotency_key` (unique per workspace), the existing `message.send` job delivers it with the consent check again; `webhook.send` writes a `workflow_deliveries` row and a `workflow.deliver` job posts it (12 attempts on the webhook backoff). A step that crashes after queueing is rolled back whole and run again; one run again over a committed row finds it and moves on. Both are tested. A webhook carries `GoHigh-Signature` (as in Events and webhooks, with the workflow's `signing_secret`, returned once on create, `POST /workflows/{id}/rotate-secret` makes a new one), `GoHigh-Idempotency-Key`, `GoHigh-Run-Id` and `GoHigh-Delivery-Id`, and the body is `{"workflow", "run", "record": {id, object, display_name}, "data"}`: only what `payload` maps leaves.
- **Versions** are immutable: `POST /workflows/{id}/versions` saves a graph as the next number (what the newest already holds changes nothing), `GET .../versions`, `GET .../versions/{n}`, `GET .../diff?from=1&to=2` (nodes added, removed and changed, with the keys that differ; where a node is drawn is not a difference). `POST .../publish {"version": 2}` points the workflow at one (any number: that is rollback). Runs in flight finish on the version they started on, unless `migrate` is sent: a run at a node the new version still has stays there on it, one at a removed node goes where `migrate` says (`{"old_node": "new_node" | "exit"}`), and a removed node with no answer is a 422 that counts its runs; `"dry_run": true` only counts. `pause` freezes the runs and stops new ones, `resume` queues them again, `DELETE` archives and cancels the runs in flight. `POST /workflows` takes `name`, `folder`, `settings`, an optional `graph` (version 1) and `note`.
- **Test runs**: `POST /workflows/{id}/test {"record_id", "version"?, "paths"?}` walks a version (the newest, a draft included) for a record, synchronously, on a virtual clock that starts at the time the consent rules read: a wait ends at once and says how many seconds it skipped, a send or a webhook says what it would send and writes no row, queues no job and calls nothing. It runs the real actions against the real record inside a savepoint that is always rolled back, so nothing is written (a test checks the whole world before and after) while conditions after an update see it and exit rules refuse for real. `paths` forces a branch (`{"split_node": "b", "event_wait": "event"}`). The trace is saved as a run with `test` set, which the runs list hides unless `test=true`.
- **Why did it not enter**: `GET /workflows/{id}/explain?record_id=` answers from the check log (each check: event, hit or miss, outcome `entered`, `filter`, `object`, `data`, `reentry`, `running`, `self`, `no_record` or `error`, and the clause), or, when there is none, judges the trigger against the record now; `answer` is a sentence.
- **What uses it**: `GET /workflows/refs?kind=tag|field|stage|user|channel|form|calendar&id=` (or `&key=`, a field is `contact.email`) lists the workflows, versions and nodes that use it, from `workflow_refs`, extracted when a version is saved.
- **Events**: `workflow.created`, `workflow.updated` (name, folder, settings, status, signing secret rotation: a change, never the secret), `workflow.version_created`, `workflow.published` (with how many runs it moved or exited), `workflow.run_started`, `workflow.run_completed` (`completed` or `exited`), `workflow.run_failed`, `workflow.run_cancelled` and `workflow.step_failed`. Webhooks can subscribe to them; workflow events never start workflows.
- **Not built yet**: the canvas builder, subflows (a node saves but does not publish), loops over records, AI steps and the AI generator, an inbound webhook trigger, code steps, a cost preview, stop on response, a time window per workflow beyond the channels' quiet hours, goals that wait until met, bulk retry and bulk enrollment, and email, Slack and calendar actions beyond the first nine.
